# ТЗ: перенос нового дизайна CeramicaDecor на текущий Laravel-сайт без поломки админки

## 1. Короткая суть задачи

Нужно не запускать отдельный новый сайт и не переделывать админку с нуля, а аккуратно заменить публичную часть текущего сайта `ceramicadecor.ru` на новый дизайн.

Текущий сайт работает на Laravel и связан с админкой через серверные шаблоны `view`/Blade. У админки нет отдельного API, из которого новый фронтенд мог бы сам “забирать данные”. Поэтому готовую HTML/CSS/JS-верстку нужно разобрать на компоненты и встроить в существующие Laravel-шаблоны, сохранив текущие маршруты, структуру данных, формы, фильтры, SEO и логику админки.

Главный риск: если сделать просто статическую версию или отдельный фронтенд, админка не сможет нормально управлять контентом, каталогом, карточками, формами и URL. Правильный путь: сначала получить полную статическую верстку всех типов страниц, затем интегрировать ее в текущие Blade-шаблоны Laravel.

## 2. Исходные вводные

Текущий сайт: https://ceramicadecor.ru/

По текущей информации:

- сайт сделан на Laravel;
- публичная часть рендерится через большое количество шаблонов страниц, разбитых на части;
- админка не имеет полноценного API для отдельного SPA/фронтенда;
- обновление дизайна означает замену HTML-разметки, CSS, JS и Blade-шаблонов публичной части;
- URL сайта менять нельзя;
- карточки товаров/работ должны иметь отдельные индексируемые страницы, а не существовать только во всплывающем окне;
- лайт-версия нового дизайна уже есть в виде статической HTML/CSS/JS-версии и должна быть передана локально как исходный дизайн-референс.

## 3. Цель работы

Сделать новый дизайн публичного сайта CeramicaDecor на базе текущего Laravel-проекта так, чтобы:

- админка продолжила работать без изменения привычного сценария наполнения;
- все текущие публичные URL остались прежними;
- все данные из админки продолжили выводиться на сайте;
- формы, заявки, WhatsApp/телефонные ссылки, избранное/корзина, фильтры и пагинация продолжили работать;
- SEO-страницы, карточки, категории, блог, работы и служебные страницы сохранили индексацию;
- новый дизайн был применен ко всем ключевым типам страниц, а не только к главной.

## 4. Что передать исполнителю/Codex перед началом

### 4.1. Архив текущей лайт-версии нового дизайна

Передать локально архив, например:

`ceramicadecor-light-static.zip`

В архиве должны быть:

- все `.html`-страницы лайт-версии;
- папки со стилями: `css/`, `scss/` или аналог;
- папки со скриптами: `js/`;
- изображения и видео/иконки: `images/`, `img/`, `assets/`, `fonts/`, `video/`;
- исходники, если есть: Figma export, SVG, PSD, шрифты, README;
- инструкция запуска, если используется сборщик: `package.json`, `vite.config.*`, `webpack.*`, `gulpfile.*` и т.д.;
- список страниц лайт-версии и назначение каждой страницы.

Если лайт-версия сейчас лежит в папке, нужно передать ее без потери структуры:

```bash
cd /path/to/light-version
zip -r ceramicadecor-light-static.zip . -x "node_modules/*" ".git/*" ".DS_Store"
```

Отдельно передать, если есть:

- ссылку на Figma/макеты;
- список отличий между КЗ-версией и будущей РФ-версией;
- список страниц, которые еще не готовы в новом дизайне;
- комментарии по спорным местам: карточка товара, каталог, фильтры, модальные окна, формы.

### 4.2. Доступ к текущему Laravel-проекту

Нужен доступ к репозиторию или архиву текущего сайта:

- Laravel-код;
- папки `resources/views`, `routes`, `app`, `public`;
- текущие CSS/JS/assets;
- `.env.example` без секретов;
- инструкции запуска локально;
- дамп тестовой базы или staging-база без приватных данных;
- доступ к staging-серверу, если локально полностью поднять проект нельзя.

Важно: не работать сразу на production.

### 4.3. Список текущих URL, которые нельзя менять

Нужно выгрузить текущую карту сайта и использовать ее как контрольный список:

```bash
curl -L https://ceramicadecor.ru/sitemap.xml
curl -L https://ceramicadecor.ru/sitemap0.xml > current-sitemap0.xml
```

Все URL из sitemap должны либо открываться после обновления, либо иметь заранее согласованный редирект. По умолчанию редиректы не нужны, потому что задача - сохранить текущие URL.

- какие шаблоны отвечают за блог/статьи;

- где лежат общие части: header, footer, меню, хлебные крошки, формы, карточки, фильтры, пагинация;
- какие данные приходят из контроллеров в каждый шаблон;
- какие JS-сценарии уже используются: слайдеры, галереи, модалки, фильтры, формы, избранное, корзина.

### Этап 2. Разбор лайт-версии на переиспользуемые компоненты

Из статической лайт-версии выделить:

- общий layout;
- header;
- desktop/mobile menu;
- footer;
- карточку товара/работы;
- карточку категории;
- хлебные крошки;
- блок hero;
- блоки преимуществ/описания;
- галерею/слайдер;
- фильтры;
- пагинацию;
- формы заявки;
- модальные окна;
- кнопки WhatsApp/телефона;
- состояния пустого списка, ошибки, загрузки, успешной отправки формы.

Не копировать HTML в каждый Blade-файл целиком. Нужно сделать нормальные частичные шаблоны/partials, чтобы общий header/footer/карточки не дублировались.

### Этап 3. Интеграция дизайна в Laravel views

Встроить новый HTML в существующие Blade-шаблоны:

- заменить статический текст на переменные из текущих моделей/контроллеров;
- заменить статические картинки на данные из админки;
- сохранить текущие циклы вывода товаров/работ/статей;
- сохранить текущие условия отображения цен, характеристик, описаний, галерей;
- сохранить текущие формы и обработчики;
- сохранить CSRF-токены Laravel;
- сохранить текущую систему генерации номеров обращений, если она есть;
- сохранить текущие ссылки на WhatsApp с номером обращения, если это уже работает;
- сохранить микроразметку/SEO-поля, если они есть;
- сохранить `title`, `description`, `canonical`, `robots`, Open Graph, если они управляются из админки.

Нельзя:

- менять структуру базы без отдельного согласования;
- ломать существующие роуты;
- заменять серверный сайт на отдельный SPA без API;
- делать карточки товаров только модальными окнами;
- хардкодить данные, которые сейчас редактируются из админки;
- удалять старую функциональность только потому, что ее нет в лайт-версии.

### Этап 4. Сохранение URL и SEO

Критически важно:

- все существующие URL должны остаться прежними;
- ссылки в меню должны вести на текущие адреса;
- ссылки карточек должны вести на отдельные страницы карточек;
- хлебные крошки должны использовать текущую иерархию;
- пагинация и фильтры должны работать с текущими параметрами;
- страницы, которые были в sitemap, должны остаться доступны;
- не закрывать важные страницы от индексации;
- не создавать дублей с новыми URL без canonical.

Примеры важных URL-групп:

- `/`;
- `/izrazcy/`;
- `/izrazcy/odnotonnye-izraztsy/`;
- `/izraztsovye-kaminy/`;
- `/izraztsovye-kaminy/kaminnye-oblitsovki/`;
- `/kaminnye-portaly/`;
- `/kaminnye-topki/`;
- `/plitka-ruchnoy-raboty/`;
- `/plitka-ruchnoy-raboty/katalog-plitki-dlja-doma/`;
- `/nashi-raboti/`;
- `/nashi-raboti/.../`;
- `/projects/`;
- `/projects/.../`;
- `/blog/.../`;
- `/our_team/`;
- `/video_review/`;
- `/o-nas/`;
- `/contacts/`;
- `/politika-konfidentsialnosti/`;
- `/cookie-policy/`.

### Этап 5. Карточки товаров/работ

Требование по карточкам:

- у каждой карточки должна быть отдельная публичная страница;
- карточка товара/работы из каталога должна открываться как полноценная страница, а не как модальное окно;
- ссылка на карточку должна быть обычным `<a href="...">`, чтобы ее видели пользователи и поисковые роботы;
- страница карточки должна выводить данные из админки: название, изображения, описание, характеристики, цены, кнопки заявки/WhatsApp, связанные товары/работы;
- если в текущей РФ-версии карточка пока не готова, нужно сделать ее по логике КЗ-версии или максимально близко к утвержденному дизайну, но без потери отдельного URL.

### Этап 6. Формы и заявки

Проверить и сохранить:

- формы обратной связи;
- формы “оставить заявку”;
- формы на карточках товаров;
- формы на странице контактов;
- WhatsApp-ссылки;
- телефонные ссылки;
- согласие на обработку персональных данных;
- сообщения об успешной/ошибочной отправке;
- защиту Laravel CSRF;
- текущие интеграции отправки в почту/CRM/админку, если они есть.

Нельзя заменять рабочие формы на декоративные статические кнопки.

### Этап 7. Адаптивность

Проверить минимум:

- desktop 1440px;
- laptop 1280px;
- tablet 768px;
- mobile 390px;
- mobile 360px.

На всех размерах:

- меню открывается и закрывается;
- фильтры доступны;
- карточки не ломаются;
- длинные названия не вылезают;
- кнопки не перекрывают текст;
- формы помещаются;
- галереи/слайдеры работают;
- footer не разваливается.

### Этап 8. Производительность и assets

Нужно:

- перенести только нужные CSS/JS/assets из лайт-версии;
- убрать неиспользуемый мусор, если он явно не нужен;
- сохранить или настроить сборку ассетов Laravel/Vite/Mix, если она есть;
- не подключать тяжелые библиотеки без необходимости;
- проверить, что изображения грузятся из правильных путей;
- не ломать загрузку пользовательских изображений из админки;
- использовать версионирование CSS/JS, если оно принято в проекте.

## 6. Минимальный набор шаблонов, которые должны быть покрыты новым дизайном

Нужно покрыть не каждую отдельную страницу вручную, а каждый тип шаблона. Но после интеграции каждый URL из текущего sitemap должен открываться в новом дизайне.

7. Детальная страница работы.

10. Блог/список статей, если он есть в текущем проекте.

## 7. Проверка после интеграции

### Функциональная проверка

Проверить:

- главная открывается;
- меню открывает правильные разделы;
- все основные разделы из header/footer работают;
- каталог выводит реальные товары/работы из базы;
- фильтры меняют выдачу;
- пагинация работает;
- карточки открываются по отдельным URL;
- галереи листаются;
- формы отправляются;
- WhatsApp/телефонные ссылки корректные;
- админка после изменения контента обновляет данные на сайте;
- нет PHP/Laravel ошибок в логах.

### SEO-проверка

Проверить:

- `title` и `description` не потерялись;
- canonical корректный;
- robots не закрывает нужные страницы;
- хлебные крошки есть;
- важные H1 на месте;
- старые URL возвращают 200;
- нет массовых 404;
- sitemap после обновления не потерял важные страницы.

### Техническая проверка

Минимальные команды:

```bash
php artisan route:list
php artisan view:clear
php artisan cache:clear
php artisan config:clear
npm run build
```

Если в проекте есть тесты:

```bash
php artisan test
```

Если тестов нет, сделать ручной smoke-test по чек-листу выше.

## 8. Что считается готовым результатом

Работа считается выполненной, когда:

- новый дизайн применен на всех ключевых типах страниц;
- админка продолжает управлять контентом;
- текущие URL не изменились;
- карточки товаров/работ имеют отдельные страницы;
- формы и заявки работают;
- каталог, фильтры, пагинация, галереи работают;
- сайт корректно выглядит на desktop/mobile;
- нет критических ошибок в Laravel logs;
- есть staging-ссылка для проверки;
- есть список измененных файлов;
- есть список известных ограничений, если что-то не было реализовано.

## 11. Короткий prompt для Codex/исполнителя

Нужно интегрировать новый статический дизайн CeramicaDecor из лайт-версии в текущий Laravel-сайт `ceramicadecor.ru`.

Не делать отдельный SPA и не менять админку без необходимости. Сначала провести аудит текущих Blade-шаблонов, маршрутов и данных, затем разложить HTML/CSS/JS лайт-версии на reusable partials и встроить в существующие views. Все текущие URL сохранить. Все данные должны продолжить приходить из админки/БД, а не быть захардкоженными. Карточки товаров/работ должны иметь отдельные публичные страницы с обычными ссылками; открытие детальной карточки товара через модальное окно не использовать как сценарий каталога. Формы, фильтры, пагинация, галереи, WhatsApp/телефонные ссылки, SEO-поля, sitemap и индексация не должны сломаться.

Перед началом составить таблицу соответствия: тип страницы -> пример URL -> текущий Blade/view -> новый HTML/секция. После работы предоставить staging, список измененных файлов, список проверенных URL и результат smoke-test.
