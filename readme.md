# CeramicaDecor: статическая верстка для передачи программисту

## 1. Цель проекта

Нужно подготовить статическую верстку сайта CeramicaDecor: HTML, CSS, JS, шрифты и изображения, которые являются частью дизайна.

Эта папка не является финальной интеграцией с внутренней системой. Итоговый результат должен быть дизайн-пакетом, который можно передать программисту. Программист затем подтянет реальные данные из внутренней системы: товары, категории, цены, описания, фотографии, SEO-поля, формы и маршруты.

Главное: в верстке должен быть понятный внешний вид всех нужных типов страниц и шаблонов, но не обязательно полный реальный каталог со всеми товарами.

## 2. Что нужно передать программисту

Программист просит дизайн:

- HTML-разметку страниц и блоков;
- CSS-стили, адаптивность, сетки, цвета, типографику;
- JS для поведения интерфейса: меню, модалки, слайдеры, фильтры, пагинация, поиск как интерфейс;
- шрифты;
- картинки, которые являются элементами дизайна: логотипы, иконки, hero-фоны, декоративные изображения, демонстрационные изображения для карточек.

Не нужно передавать как обязательную часть дизайна всю контентную базу: тысячи фото товаров, все 360-фото, полный каталог изразцов, все цены и реальные карточки. Эти данные должны подключаться из внутренней системы.

## 3. Важное отличие от исходного ТЗ

Исходный файл ТЗ `ТЗ_CeramicaDecor_новый_дизайн_Laravel.md` описывает интеграцию нового дизайна в существующий Laravel-сайт без поломки админки.

Текущее уточнение меняет формат работы:

- сейчас готовится не Laravel-интеграция, а статическая верстка;
- верстка должна быть удобной для последующей привязки к внутренней системе;
- данные из внутренней системы не нужно заранее вшивать в HTML;
- хардкод товаров допустим только как демонстрационный пример шаблона;
- все динамические места должны быть понятны программисту.

Основные страницы:

Важно: в общем доступе на сайте не должно быть никаких переходов на `login.html` и `password-recovery.html`. Их нельзя добавлять в шапку, футер, модальное окно поиска, публичные CTA-блоки и публичный `sitemap.xml`.

## 5. Каталог и карточки

Все разделы каталога должны быть частью единой структуры каталога.

Большинство разделов каталога используют общий шаблон каталожной страницы. Позже можно изменить баннер, фильтры, карточки, изображения и тексты под конкретный раздел.

Раздел `Изразцы` находится внутри общего каталога, но у него отдельный дизайн карточек. Поэтому в `catalog-izrazcy.html` нужно сохранить первую страницу товаров, фильтры, пагинацию и карточку изразца как шаблон для программиста.

Для будущей интеграции важно:

- карточки товаров в каталоге должны открываться как полноценные отдельные страницы товара/изделия, а не как модальные окна;
- ссылка карточки должна быть обычным `<a href="...">` на детальную страницу, чтобы ее видели пользователи и поисковые роботы;
- модальные окна можно использовать для форм заявки, видео, поиска и вспомогательных интерфейсов, но не как основной способ открытия карточки товара;
- изображения, цены, названия, характеристики и описания должны быть заменяемыми данными из внутренней системы;
- демонстрационные карточки в HTML/JS не являются полной базой товаров.

## 6. Формы

В верстке могут быть формы на главной, странице контактов, карточках и в модальных окнах.

Формы должны показывать дизайн и ожидаемые поля:

- имя;
- телефон;
- комментарий;
- товар или страница, откуда отправлена заявка;
- согласие на обработку персональных данных.

Endpoint отправки заявок в статической верстке может быть временным. Программист должен заменить его на обработчик внутренней системы.

Нельзя превращать формы в декоративные кнопки без поведения. Даже в статике должно быть понятно, где форма, какие поля нужны и какое сообщение показывается после отправки.

## 7. Навигация

В шапке сайта должны быть основные пункты:

- каталог;
- палитра глазурей;
- реставрация;
- комплектующие;
- сотрудничество;
- о компании;
- контакты.

Пункт `Каталог` в шапке раскрывается выпадающим списком разделов каталога. Первый пункт списка — `Весь каталог`, ведущий на `catalog.html`.

В футере должен быть полный список разделов каталога и служебные ссылки.

Поиск сейчас реализован как модальное окно. Отдельная страница поиска не нужна.

Внутренние страницы `login.html` и `password-recovery.html` не должны быть доступны через публичную навигацию сайта. Ссылки на них могут использоваться только во внутренних сценариях кабинета заказов или в прямых служебных маршрутах, которые задаст программист при интеграции.

## 8. SEO-заготовки

Для статической верстки нужно оставить понятные места под SEO:

- `title`;
- `description`;
- `canonical`;
- Open Graph;
- H1;
- `sitemap.xml`;
- `robots.txt`.

В финальной интеграции программист должен подставить реальные URL, canonical, SEO-тексты и sitemap из внутренней системы.

Если в файлах встречается `DOMAIN` или пустой `canonical`, это временная заглушка, которую нужно заменить при интеграции.

## 9. Изображения и assets

Нужно различать дизайн-ассеты и контент.

Дизайн-ассеты:

- логотип;
- иконки;
- шрифты;
- hero-фоны;
- декоративные изображения секций;
- изображения, которые нужны для визуального примера карточек.

Контент:

- все реальные фотографии товаров;
- весь каталог изразцов;
- все 360-фото;
- технические фото конкретных изделий.

Контентные изображения могут оставаться в рабочей папке как демо-материал, но при передаче программисту стоит отдельно решить, какие из них действительно нужны. Огромные папки с товарными фото не должны считаться обязательной частью дизайна.

Файлы `.tmp` и `.raw`, если они есть среди изображений, не являются частью чистого дизайн-пакета и требуют отдельной проверки перед архивированием.
